Why Do We Need QoS?

Modern networks carry different types of traffic with different requirements:

🎤 Voice (VoIP)

  • Latency: <150ms (one-way)
  • Jitter: <30ms
  • Packet Loss: <1%
  • Bandwidth: Low (~30-128 Kbps)
  • Extremely delay-sensitive

📹 Video

  • Latency: <200ms
  • Jitter: <50ms
  • Packet Loss: <0.5%
  • Bandwidth: High (384 Kbps - 20 Mbps)
  • Bursty, delay-sensitive

💼 Business Apps

  • Mission-critical data
  • ERP, CRM systems
  • Database transactions
  • Moderate delay tolerance

🌐 Best-Effort Traffic

  • Web browsing
  • Email
  • File downloads
  • No special treatment
The Problem: Without QoS, all traffic is treated equally. A large file download can starve a VoIP call, causing choppy audio and dropped calls!

What is Quality of Service (QoS)?

QoS is a set of techniques to manage network resources and provide different priority to different applications, users, or data flows.

QoS Goal: Ensure that time-sensitive and mission-critical traffic gets preferential treatment over less important traffic, especially during network congestion.

QoS Can Manage:

Bandwidth
Allocate minimum guaranteed bandwidth to critical applications
Delay (Latency)
Prioritize low-latency traffic (voice, video) over bulk data
Jitter
Reduce variation in packet arrival times for real-time traffic
Packet Loss
Preferentially drop less important traffic during congestion
Key Concept: QoS doesn't create bandwidth - it manages existing bandwidth more intelligently. You can't QoS your way out of an undersized link!

Three QoS Models

Model Description When to Use
Best Effort No QoS - all traffic treated equally (default) Small networks, non-critical traffic only
Integrated Services (IntServ) Per-flow reservation using RSVP (Resource Reservation Protocol)
Guaranteed bandwidth for each flow		 Legacy - rarely used today (too complex)
Differentiated Services (DiffServ) Class-based QoS using DSCP markings
Scalable, industry standard		 CCNA Focus - Used in modern networks

DiffServ is the Standard

DiffServ is the most common QoS model used today. It classifies traffic into classes and treats each class differently based on policies.

  • Scalable: Works across large networks
  • Flexible: Multiple service levels
  • Efficient: No per-flow state tracking
CCNA Focus: You need to understand DiffServ concepts, DSCP markings, and how to configure basic class-based QoS.

The QoS Process - Three Steps

QoS implementation follows three fundamental steps:

1. Classification
Identify which packets belong to which traffic class
Tools: ACLs, NBAR, DSCP values, CoS, ports
2. Marking
Tag packets with QoS markings for downstream devices
Tools: DSCP (Layer 3), CoS (Layer 2)
3. Queuing & Congestion Management
Prioritize, queue, drop, or shape traffic based on markings
Tools: LLQ, CBWFQ, WRED, policing, shaping
Analogy: Think of an airport:
  • Classification: TSA checks your ticket to see if you're First Class or Economy
  • Marking: You get a boarding group number (1, 2, 3, etc.)
  • Queuing: Group 1 boards first, Group 2 waits, Group 3 waits longer
Classification and Marking happen at the network edge (access layer)
Queuing and congestion management happen wherever congestion occurs (typically WAN links)

Classification - Identifying Traffic

Classification is the process of examining packets and putting them into traffic classes.

Classification Methods:

Method Layer Description
DSCP Layer 3 6-bit field in IP header (most common)
IP Precedence Layer 3 3-bit field in IP header (legacy, replaced by DSCP)
CoS (Class of Service) Layer 2 3-bit field in 802.1Q VLAN tag (trunk links only)
ACLs Layers 3-4 Match by source/dest IP, port, protocol
NBAR Layer 7 Network-Based Application Recognition (deep packet inspection)
Best Practice: Use DSCP for Layer 3 classification and CoS for Layer 2 (switch-to-switch) links. DSCP values are preserved end-to-end across routed networks.
CoS Limitation: CoS only exists in 802.1Q tags, so it only works on trunk links. Access ports have no VLAN tag, so no CoS field!

AF Classes - Assured Forwarding

Assured Forwarding provides 4 classes with 3 drop precedences each:

Class Low Drop (AF_1) Medium Drop (AF_2) High Drop (AF_3)
Class 4 AF41 (34) AF42 (36) AF43 (38)
Class 3 AF31 (26) AF32 (28) AF33 (30)
Class 2 AF21 (18) AF22 (20) AF23 (22)
Class 1 AF11 (10) AF12 (12) AF13 (14)
AF Naming: AFXY
X = Class (4 is highest, 1 is lowest)
Y = Drop Precedence (1 = low drop probability, 3 = high drop probability)
Example: AF31 means:
- Class 3 (medium-high priority)
- Drop precedence 1 (low drop probability)
- DSCP decimal value: 26
Drop Precedence: During congestion, AF_3 packets are dropped first, then AF_2, then AF_1. Higher drop precedence = more likely to be dropped.

CoS - Class of Service (Layer 2)

CoS is the Layer 2 equivalent of DSCP, used on 802.1Q trunk links.

CoS Field: 3 bits in the 802.1Q VLAN tag (PCP field)
Range: 0-7 (8 possible values)
Where: Only on trunk links (access ports have no VLAN tag!)

Standard CoS Values:

CoS Name Traffic Type Maps to DSCP
7 Network Control Reserved (routing protocols) CS7 (56)
6 Internetwork Control Reserved (network management) CS6 (48)
5 Voice VoIP audio EF (46)
4 Video Video conferencing AF41 (34)
3 Critical Applications Mission-critical data AF31 (26)
2 Excellent Effort Business-important data AF21 (18)
1 Background Bulk data, backups AF11 (10)
0 Best Effort Default traffic DF (0)
CoS Limitation: CoS is Layer 2 only and doesn't survive routing. Use DSCP for end-to-end QoS across routed networks.

❌ Untrusted Devices

  • End-user PCs
  • Guest devices
  • Unknown devices

Action: Ignore/overwrite markings, classify and mark at access switch

✅ Trusted Devices

  • IP phones (Cisco)
  • Video endpoints
  • Other network devices

Action: Trust incoming markings, preserve them

Cisco IP Phone Exception: You can configure a switch port to trust CoS/DSCP markings from a Cisco IP phone while ignoring markings from the PC connected to the phone.
Best Practice: Set the trust boundary as close to the source as possible (usually the access switch). Don't trust end-user devices unless necessary.

Queuing - Managing Traffic Flow

Queuing determines which packets get transmitted first when an interface becomes congested.

Queuing Algorithms:

Method How It Works When to Use
FIFO First In, First Out - simple queue Default, no QoS (not recommended)
PQ (Priority Queuing) 4 queues, services high-priority queue first Legacy (can starve low-priority traffic)
WFQ (Weighted Fair Queuing) Automatic per-flow fairness Default on serial links <2 Mbps
CBWFQ Class-Based WFQ - define classes with guaranteed bandwidth Modern QoS - custom classes
LLQ CBWFQ + strict priority queue for delay-sensitive traffic RECOMMENDED - Voice/video + data

LLQ is the Gold Standard

Low Latency Queuing (LLQ) combines:

  • Strict priority queue for voice/video (guaranteed low latency)
  • Class-based queues for data (guaranteed bandwidth)
  • Policing to prevent priority queue from starving others

Congestion Avoidance - WRED

WRED (Weighted Random Early Detection) prevents TCP global synchronization by intelligently dropping packets BEFORE queues fill.

Problem Without WRED: When a queue fills, tail drop occurs - ALL new packets are dropped. This causes all TCP sessions to slow down simultaneously (global synchronization), then speed up together, causing oscillation.

Tail Drop (Bad)

  • Queue fills to 100%
  • All new packets dropped
  • All TCP sessions slow down together
  • Then all speed up together
  • Causes oscillation and inefficiency

WRED (Good)

  • Monitors queue depth
  • Randomly drops packets as queue fills
  • Different drop probability per DSCP
  • Lower-priority traffic dropped first
  • Prevents global synchronization
WRED Drop Thresholds:
- Min Threshold: No drops below this queue depth
- Max Threshold: Drop probability increases between min and max
- Above Max: All packets dropped (tail drop)
WRED and Voice: NEVER use WRED on voice traffic! Voice is UDP and doesn't retransmit. Drops = bad audio. Use WRED only on TCP data classes.

Traffic Conditioning - Policing vs Shaping

Both limit traffic rates, but handle excess traffic differently:

🚨 Policing

  • Action on Excess: DROP or REMARK
  • Buffering: None
  • Effect: Can cause packet loss, TCP retransmissions
  • Where: Service provider edge, ingress
  • Direction: Inbound or outbound
Example: ISP limits your upload to 10 Mbps. Excess packets are dropped.

📊 Shaping

  • Action on Excess: BUFFER (delay)
  • Buffering: Yes, uses queues
  • Effect: Increases latency, but fewer drops
  • Where: Customer edge, egress
  • Direction: Outbound only
Example: You shape outbound to 10 Mbps to match ISP's limit. Excess buffered, not dropped.
When to Use Each:
Policing: Enforce limits on untrusted traffic (ingress from customers/internet)
Shaping: Smooth outbound traffic to avoid being policed by downstream device

Token Bucket - How Policing/Shaping Works

Both policing and shaping use the token bucket algorithm to measure traffic rates:

Token Bucket Concept:
- Tokens are added to a bucket at a configured rate (e.g., 1 token per bit)
- Each packet needs tokens equal to its size to be transmitted
- If enough tokens exist, packet is sent and tokens are removed
- If not enough tokens, packet is dropped (policing) or buffered (shaping)

Key Parameters:

CIR (Committed Information Rate)
Target average rate in bps - tokens added at this rate
Bc (Committed Burst)
Bucket size in bits - how many tokens the bucket can hold
Be (Excess Burst)
Additional tokens for temporary bursts (policing only)
Example: CIR = 1 Mbps, Bc = 8000 bits
- Normal traffic: Uses tokens as they arrive at 1 Mbps
- Burst: Can send 8000 bits instantly (if bucket is full)
- Sustained excess: Tokens depleted, packets dropped/delayed

Marking Best Practices

  • Mark as close to the source as possible
  • Use standard DSCP values (EF, AF classes)
  • Trust IP phones but not PCs
  • Document your marking scheme

Key Takeaways - QoS Essentials

🎯 Why QoS?

  • Voice requires <150ms latency, <30ms jitter
  • Limited bandwidth must be managed
  • Different apps have different needs
  • QoS prioritizes critical traffic

📋 Classification & Marking

  • DSCP: 6-bit field, 0-63 (Layer 3)
  • EF (46): Voice priority
  • AF classes: 4 classes × 3 drop levels
  • CoS: 3-bit field, 0-7 (Layer 2, trunks only)

⚙️ Queuing

  • LLQ: Best for voice + data
  • Priority queue for delay-sensitive traffic
  • CBWFQ for guaranteed bandwidth
  • WRED prevents TCP global sync

🎯 Key Differences

  • Policing: Drops excess (ingress)
  • Shaping: Buffers excess (egress)
  • Trust Boundary: Access layer
  • MQC: class-map → policy-map → service-policy

🎓 QoS is essential for voice/video - Know DSCP values, LLQ, and policing vs shaping!
